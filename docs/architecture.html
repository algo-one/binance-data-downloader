binance-data-downloader — how it actually works

One clean stack of candles, out of three sources that each lie a little.

A Go library that turns a symbol, an interval and a time range into a verified, gap-free slice of Binance kline data — fast on the first run, ten times faster on the second. This page walks through how the fifteen finished stages fit together, with the numbers that shaped each decision.

§1

Where the data comes from

Binance publishes the same candles in three different places, and no single one of them is enough on its own. Bulk archives are monthly and daily ZIP files — the bulk of any history, immutable the moment they're published. The REST API covers the tail: archives lag real time by about a day, so anything more recent has to be paginated out of the live endpoint. And a plain S3 bucket listing answers a question neither of the other two will: what has Binance actually published?

That third source sounds like a nicety until you notice the archive has holes. Out of BTCUSDT's 105 published monthly files, two are silently missing — no 404 pattern, no calendar rule predicts them. The only way to know is to ask the bucket what it holds, before fetching anything.

Binance's own sharp edges

  • An unknown symbol isn't a 404. A misspelt prefix returns HTTP 200 and an empty, well-formed listing — indistinguishable from "this pair simply has no data yet."
  • The plain hostname lies. Asking data.binance.vision for a listing returns its HTML file-browser page, not XML — only the regional S3 endpoint answers correctly.
  • A failed lookup is never read as an empty one. The library treats "the bucket didn't answer" and "the bucket answered with nothing" as two different, non-interchangeable outcomes.
§2

The pipeline: plan, execute, reduce

Every request goes through the same three stages. Plan is pure arithmetic — no network calls at all — turning a date range into a flat list of chunks. Execute is the only stage that touches the network: a bounded pool of workers fetches each chunk, with duplicate work collapsed automatically. Reduce stitches the results back into one ordered, gap-free slice.

Keeping the pool flat — one queue of same-sized chunks, never a group nested inside another — is what makes the concurrency limit actually hold. A limit with an outer unit (a month) waiting on inner ones (its days) can deadlock the moment the outer unit is holding a permit it isn't using.

§3

Downloading

All network traffic goes through one shared http.Client for the life of the process, so TCP and TLS handshakes — 100–200 ms apiece — happen once per host, not once per archive. Every response body is read to completion before it's closed, because a half-read body forces Go to drop the connection instead of pooling it for reuse.

Archives are hashed as they stream: one copy, written simultaneously to disk and into a running SHA-256, so verifying every download costs nothing extra. The 91-byte .CHECKSUM sidecar is fetched first, so an unpublished month costs one tiny request instead of a large transfer that ends in a 404.

§4

Parsing

An archive is a ZIP holding one CSV with twelve columns. Reading it is easy; trusting it is not, and three things about it were bugs in the implementation this library replaces. The header is sniffed per file — spot archives carry none, futures archives do. The timestamp unit is detected per row, because Binance switched from milliseconds to microseconds on 2025-01-01 mid-file. And every candle is checked against the interval grid and the price relationships that must hold between its eight decimal fields — low is the lowest of the four prices, nothing is negative, taker-buy volume can't exceed the total.

Three intervals anchor their grid somewhere other than the Unix epoch — getting this wrong turns a valid candle into a rejected one, silently.

IntervalGrid anchor
1s … 1dMultiples of the interval from midnight UTC
3dThree-day multiples from 1970-01-02 — doesn't restart monthly
1wMonday 00:00 UTC
1moThe 1st of the month, 00:00 UTC
§5

Two-tier caching

Tier 1 is the archive exactly as Binance sent it — ZIP plus checksum sidecar. Tier 2 is a derived Parquet file, its footer stamped with the archive's hash and the codec version that built it. A hit compares that stamp against the sidecar's hash and reads Parquet columns directly — the archive itself is never opened, which is what makes a hit ten times cheaper than a cold parse.

Every write lands in a temp file first, then a rename — so a crash mid-write leaves either the old file or the new one, never a torn one. And a lookup registers in-flight before any I/O starts, so a saturated pool can't let two workers download the same archive twice.

§6

Reclaiming disk, without breaking a single read

If a hit never opens the archive, the archive doesn't have to still be there. That fell out of the cache design and sat unused for four stages — a test has asserted since tier 2 existed that a cache whose ZIP has been deleted still serves every read that doesn't need a rebuild. What was missing was a way to ask for it: bmd cache reports, bmd prune acts.

The pruner doesn't get its own opinion of "usable". An archive may go only when the Parquet beside it would be accepted by a read, and that is the same two footer gates the read path opens with — the stamp must name this archive's hash and this binary's CodecVersion, and the schema must be the one this package writes. One copy of each, called from both places. A pruner with a second, looser notion of usable is one that eventually deletes an archive that was about to be needed.

Only the .zip goes. The sidecar stays, because its hash is what validates the Parquet; the Parquet stays, because it is what answers reads. Deleting either would strand the entry as completely as deleting both.

The invariant is a test, not a comment

  • Prune, then read, then count requests. A prune that deleted something a read needed would still return the right candles — by downloading them again. A test comparing only the candles passes on a cache that has silently started paying for the network on every hit.
  • -n is how you look first. bmd prune deletes; the dry run reaches every verdict and touches nothing. A command named prune that refuses to prune unless asked twice is worse.
  • What stays open: the gates read the footer, not the pages. Bit rot inside a data page surfaces on a later read, through Parquet's own per-page CRC. Closing that means decoding every cached file to answer a question about disk space.

The other 60% is the data, and that is a second command

Pruning gives back the archives. Nothing gave back the data, so the cache only ever grew. bmd evict removes whole entries — archive, sidecar and Parquet together — and it is deliberately not a flag on prune: a prune cannot cost you data, an eviction is the removal of data, and a guarantee that holds for half of a command's behaviour is not one anybody can lean on.

There is no automatic expiry, and that is a finding rather than a gap. Expiring by file age keys on when an entry was downloaded, not when it was used — so the symbol-month a backtest reads on every run expires on schedule while one fetched yesterday and never opened again survives. A least-recently-used size cap needs a recency signal the filesystem does not reliably give: access times are off or coarse on most Linux setups, so the library would have to write on every cache hit to record one, against a read path whose whole claim is that a hit touches the sidecar and a footer and nothing else. What the caller has instead is knowledge of its own window, so eviction takes a selection.

Three things the selection had to get right

  • A zero EvictOptions is an error, not "everything". The zero value is what a caller gets by forgetting to fill the struct in, and this is the one place in the package where that mistake cannot be undone. All is a separate word, and cannot be combined with a filter.
  • Before bounds the data, not the file. An entry goes only if it ends at or before the instant given, so a bound of 2024-01-15 keeps January's monthly archive: half of it is still wanted and a file is not divisible. This is why -before reads a bare date as midnight where -end stretches one to the end of the day.
  • A pruned entry is still an entry. Everything a prune has been over has no .zip, which is most of an old cache — so the walk is over directories, grouping files by their shared stem, rather than looking for archives. Anchoring on the archive would skip exactly the entries retention exists to remove, and report success.
§7

The REST tail, and its fallback ladder

Archives lag real time by about a day, so the plan never assumes an archive exists — it asks the listing, and falls back when reality disagrees. A month that isn't published becomes its days; a day that isn't published becomes a paginated REST range, which always answers — 200 and an empty array rather than a 404 — so the ladder never runs out of rungs.

The one endpoint with a quota

  • 6000 request-weight per minute, per IP. One klines call costs 2. The library paces itself at 40/s against a ceiling of 100, deliberately leaving most of the budget for anything else on the same machine.
  • 429 means slow down; 418 means stop. Ignoring a 429 for too long earns an IP ban running two minutes to three days — punishing the address, not the process, so it can lock out a live trading bot sharing the host.
  • The forming candle is always dropped. REST returns the interval currently in progress; its volume is still moving, so it's held back until intervalEnd(OpenTime) has actually passed.

The quota reading is reported, not acted on

X-MBX-USED-WEIGHT-1M says how much of the 6000 this IP has spent in the current minute. It is the only visibility this library has into a budget metered per address rather than per process — which makes it the one measurement that can see what no amount of local accounting can: a second backtest, another copy of this library, or a live trading bot drawing on the same quota. The limiter's job is to keep that number low; this is how you find out when that is not working.

It was decoded onto vision.KlinesPage, tested, and read by nobody, with a comment saying a later stage would make it visible. That is this document's own accepted-and-ignored defect, in the one place where the ignored value is the only evidence there is. restFetcher.klines now logs it at debug for every page, and once per fetch at warn past four fifths of the quota.

Three decisions inside that

  • 4800 is sized against what this library can produce, not as a round fraction. A minute of the loader running flat out at the default pace accounts for 2400 of the 6000. A reading of 4800 therefore means a burst worth knowing about or — far likelier — company on the address.
  • The warning is per fetch, not per page. The condition is a property of the minute rather than of the page that observed it, so a range crossing the threshold on its first page crosses it on all of them. A warning repeated ninety-nine times is a warning nobody reads.
  • Zero is not a measurement. The field is zero when the header was absent or unreadable, and one request always costs KlinesWeight — so a zero is reported as nothing at all rather than as "nothing has been spent".

Reporting rather than reacting is the same division of labour the rest of the package keeps. A page knows what one request cost; only the layer owning the pipeline can decide the pipeline should slow down, and that layer already has the server's own word for it in the 429 handling. This is the diagnostic that explains why that fired, or that it is about to.

The rate is settable, and only downwards

WithRateLimit(weightPerSecond) replaces the sustained rate for one loader. The unit is Binance's own — REQUEST_WEIGHT, of which a klines call costs KlinesWeight — rather than requests per second, so the number in the option is the number in the quota and neither has to be re-derived when the other changes.

The argument for having it is the argument that sets the default low. The quota is per IP, everything on the machine draws from the same 6000, and the default cannot know how much company it has: 40 is a guess that leaves room, not a measurement. A caller who does know — because the history download shares an address with something latency-sensitive — is the only one who can say so.

Rates above the quota's own 100 per second are rejected, not clamped. There is no rate above it Binance permits, so accepting one would accept a setting that cannot be honoured, and clamping silently would have the option report success for a policy it did not apply. The ceiling is the quota rather than the default, so raising toward it stays possible.

vision.BurstFor pairs the burst to the rate — half a second's worth, floored at one klines call, which yields exactly DefaultBurst at the default rate. The floor has teeth: WaitN errors rather than waits when the weight exceeds the burst, so a smaller bucket would refuse every request forever instead of pacing it. The option opts out of the process-wide limiter, and that is documented at the call site, because two buckets each honouring the rate permit twice it.

§8

Concurrency, without the deadlock

The worker pool is deliberately flat — every chunk, whether it's a whole month or a REST page, competes for the same set of permits. Nesting a limit inside a limit is the classic way to deadlock: an outer task can hold a permit while merely waiting on its own inner tasks to get one.

Permits are handed out in chunk order, by a single producer, before any worker starts — which is what lets Stream consume results in order while bounding memory to the concurrency limit rather than the length of the range. And a partly-wanted month is fetched whole only once at least half of it is actually requested and the listing confirms it exists — below that threshold, days are cheaper; above it, one archive beats fifty separate requests.

§9

Why the package layout looks the way it does

The obvious layout — every internal piece under internal/ — doesn't compile. The loader needs to call the planner, and the planner needs the same Kline and Interval types the loader exports: that's an import cycle. The fix wasn't a workaround, it was a rule: a package moves under internal/ only if it needs no domain types at all.

plan and vision qualify — one does calendar arithmetic, the other speaks raw URLs and bytes — so the compiler itself guarantees neither can ever import the root package back. codec, cache and restapi need Kline directly, so they stay in the root package, just unexported — invisible to consumers either way, but documented with their real field names instead of rendering as a bare type alias.

§11

What it looks like to call

The public surface is small on purpose: a Loader, a Request, and three ways to consume the result — Fetch for one range, FetchAll for many at once (deduplicated across the whole batch for free), and Stream for a range too large to hold in memory at once.

loader, _ := binancedata.NewLoader( binancedata.WithCacheDir("./cache"), binancedata.WithConcurrency(8), ) klines, err := loader.Fetch(ctx, binancedata.Request{ Symbol: "BTC/USDT", Interval: binancedata.Interval1h, Market: binancedata.MarketSpot, Start: time.Date(2024, 1, 1, 0, 0, 0, 0, time.UTC), End: time.Date(2024, 12, 31, 23, 59, 59, 999999999, time.UTC), })

A request is closed on both ends — End is the open time of the last candle you want, so Start == End legally asks for exactly one.

The last five exist because the CLI could not otherwise be a thin shell over the library — anything bmd can do has to be reachable from Go code, and cmd/bmd sees only exported identifiers.

§12

Six commands, and one of them is a rate-limit decision

bmd holds no logic of its own. Every command is a thin rendering of a library call, which is the constraint that drove six small additions to the public API rather than a second implementation inside the tool.

Why one process downloads many symbols — and many intervals

Binance enforces REQUEST_WEIGHT per IP address, and the library's limiter is process-wide for exactly that reason: two limiters each honouring 40 weight per second permit 80 against a ceiling of 100 — each correct alone and wrong together. Until the tool took a list of symbols, the only way to download several was several bmd processes. Three of them sit at 120 against that ceiling, and Binance answers persistent excess with an HTTP 418: an address ban lasting two minutes to three days. The tool's only multi-symbol shape was the shape that breaks its own limiter.

That argument is about processes. It says nothing about symbols — which is why -interval is a list too. A shell loop over intervals is three limiters exactly as three symbols in three processes were, so fixing only the symbol spelling left the same hazard standing behind the other flag. Both flags now take a list, and every pair of the two is downloaded: two symbols at three intervals is six downloads, in symbol order, each to its own file. Pairing the lists off positionally instead would require them to be the same length, and would quietly turn two symbols at one interval into one download.

bmd download -symbol BTC/USDT,ETH/USDT,SOL/USDT -interval 1h,1d \ -start 2024-01-01 -end 2024-03-31 -out ./data # one process, one limiter, one (symbol, interval) pair at a time

Three decisions inside that loop

  • Streaming, not FetchAll. FetchAll returns every candle of every symbol resident at once; five years of minute candles for one symbol is already about 820 MB. And a list of distinct symbols has nothing to deduplicate, which is all FetchAll would add. The limiter comes from being one process, not from which method it calls.
  • Sequential, not concurrent. The loader's semaphore already spans calls, so one symbol's chunks saturate the pool for any range worth downloading. Running symbols in parallel would need a second bound outside the library's — the nested limit §8 exists to warn about.
  • One download failing does not abandon the rest, and nothing is silent: the failure is printed, counted, and reaches the exit status. A cancellation is the exception and ends the run, or Ctrl-C would be reported as every remaining download having failed.

Every setting is honoured, or it is not offered

A flag a command advertises and then ignores costs a debugging session to discover, so each command registers only what it acts on: bmd list takes no -cache-dir, because it opens no cache, and no -concurrency, because it makes no parallel fetches. The same rule governs a flag's value. -concurrency 0 is a usage error rather than a silent fall back to 8, and so is -cache-dir "" — which is what -cache-dir "$CACHE_DIR" becomes when the variable is unset. Defaulting quietly there is the dangerous reading: the caller believes they named a directory, and the default is the user's real cache.

The cache directory can also come from the environment, and the same rule follows it there. BMD_CACHE_DIR names it when the flag is absent — flag, then variable, then os.UserCacheDir — and the lookup asks the command's own FlagSet whether -cache-dir was registered at all. So bmd list cannot see the variable either, and neither can a future command that does not take the flag. A variable set but empty is a usage error for the reason the flag's empty string is one: export BMD_CACHE_DIR="$CACHE_DIR" with CACHE_DIR unset exports an empty string and the shell says nothing.

The CLI reads it; the library does not. binancedata is imported by other programs, and a package that reads the environment on its own lets a variable exported for an unrelated reason redirect where its caller writes files. Go code says where its cache lives by calling WithCacheDir. A person says it by exporting this.

bmd cache # ~/Library/Caches/bmd BMD_CACHE_DIR=/mnt/big-disk/bmd bmd cache # the variable BMD_CACHE_DIR=/mnt/big-disk/bmd bmd cache -cache-dir /tmp/x # /tmp/x — the flag wins BMD_CACHE_DIR="" bmd cache # usage error, exit 2

§13

Two displays, and only one of them is a dependency

Every slow command used to print nothing until it finished. progress.go draws a progress bar for bmd download; spinner.go draws an indeterminate spinner for everything else slow. Both write to stderr, both draw only on a terminal, and both erase themselves — so a piped or redirected run is byte-for-byte what it was before either existed.

# on a terminal — a real fraction, because Progress carries Done and Total BTCUSDT 1h [######## ] 50% archive 2024-06-01 44640 candles # redirected — unchanged since the CLI shipped, so stderr stays greppable [ 6/12] BTCUSDT 1h archive 2024-06-01 44640 candles # nothing here reports a total, so: a spinner with a count that has no ceiling ⠹ verifying cached archives — 341 checked (852.5 MB)

Why the bar is hand-rolled and the spinner is not

  • The library's redraw does not erase to end of line. fortio.org/progressbar was tried for the bar first. It writes a carriage return and the new frame, so a frame narrower than the one before it — 44640 candles this month, 24 the next — leaves the wider frame's tail on screen: 24 candleses.
  • The fix was already in the file. Padding every frame out to the widest seen so far is what a width field does, and this file had one. A [#### ] string plus that field was less code than working around the erase.
  • The spinner keeps the library, because its glyph never shrinks. One column wide, always. Its label can shrink — verify and prune carry a byte total that turns 1023.9 MB into 1.0 GB — so setPrefix pads the label the same way the bar pads its frame.

A spinner, not a bar, and that is an honesty argument

bmd list makes up to seven bucket listings back to back. verify, cache, prune and evict each walk the whole cache directory — verify re-hashing every archive, the longest thing this tool does. A download's planning phase, before the first chunk event, is the same kind of gap. None of them reports a total before it starts, so a percentage would be invented, and an invented "70%" that then sits still is worse than an honest spinner. verify and prune do put a running count on the label — a true number that happens to have no ceiling.

Gated on -verbose on every command, because that flag routes the loader's slog stream to stderr and a spinner redrawing the same stream would scribble over the log lines it was asked for. list and cache have no -quiet to gate it against and need none: a spinner that erases itself is not something a redirected run ever sees.

The animation is a goroutine, and every write to the stream is serialised. list and cache have no loop to drive a spinner from, so it ticks on its own goroutine — and that goroutine is the only thing writing the stream while the spinner runs. stop waits for it before writing the erase, and a command that must print a real line mid-walk — a verify failure, a prune "kept" — stops, prints, and starts a fresh spinner rather than writing around a live one. No data race, which -race confirms against a forced-on spinner in the tests.

One dependency, and only for the spinner. fortio.org/progressbar has no dependencies of its own and a go 1.18 floor, so it adds a single line to the module graph and does not move the Go floor. Those are the two things that got a cosmetic dependency past the small-module-graph rule.
